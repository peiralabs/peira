# Declared system dependencies of the AppImage — the audited NEEDED closure
# of the main binary plus every bundled library (tool/build_appimage.sh fails
# the build if the closure grows beyond this file plus the bundled set).
#
# Runtime services the libraries below imply (not expressible as sonames):
#   - glibc at least as new as the build host's (AppImages inherit the
#     build host's floor — build on the oldest supported base)
#   - an X11 or XWayland session (CEF renders via X11)
#   - a D-Bus session bus and a Secret Service provider (GNOME Keyring,
#     KWallet 5.97+, or KeePassXC) — libsecret is bundled, the daemon is not
#   - unprivileged user namespaces enabled for CEF's sandbox (an AppImage
#     cannot ship a setuid chrome-sandbox); most modern distros enable this
#
# glibc / toolchain runtime — never bundle
ld-linux-x86-64.so.2
libc.so.6
libdl.so.2
libm.so.6
libpthread.so.0
libgcc_s.so.1
libstdc++.so.6
libz.so.1
libexpat.so.1
# libgcrypt enters via bundled libsecret; base-system everywhere (systemd)
libgcrypt.so.20

# GTK 3 stack — provided by the gtk3 package on every distro; bundling GTK
# into AppImages is unsupported upstream and breaks theming/portals

# libjvm.so — NOT host-provided, and never loaded on Linux. It enters only via
# the jni / jni_flutter FFI plugin that path_provider_android drags in
# transitively (jni_flutter wrongly registers for Linux desktop). On Linux,
# path_provider resolves to path_provider_linux, so the jni .so is never
# dlopen'd and libjvm is never resolved at runtime — it is NEEDED by that
# plugin .so only, not by the main binary. Declared (never bundled) because
# bundling a JVM is absurd and the reference is dead on this platform. Revisit
# if path_provider_android / jni_flutter stop registering for Linux.
